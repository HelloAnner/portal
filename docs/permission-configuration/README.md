# 权限配置

## 功能定位

权限配置用于控制用户在门户中能看到哪些系统、能进入哪些系统，以及进入子系统后具有什么身份和权限。

门户超级管理员通过该功能统一配置企业内部系统访问关系。

## 权限层级

门户权限建议分为四层：

1. 系统可见权限。
2. 系统访问权限。
3. 子系统角色权限。
4. 子系统模块或资源权限。

## 系统可见权限

系统可见权限决定用户是否能在门户首页或系统目录中看到某个子系统入口。

如果用户不可见某系统，门户不展示该系统入口。

## 系统访问权限

系统访问权限决定用户是否能点击并进入某个子系统。

系统可见不等于系统可访问。某些场景中，门户可以展示系统但提示用户申请权限；也可以直接隐藏未授权系统。

具体展示策略由产品实现决定，但权限模型需要支持二者区分。

## 子系统角色权限

子系统角色用于描述用户进入某个系统后的身份。

示例：

- `northline:user`
- `northline:admin`
- `documind:user`
- `documind:knowledge-admin`

这些角色由门户配置并下发，子系统消费后决定展示哪些页面和操作入口。

## 模块或资源权限

对于更细粒度的管理场景，门户需要支持模块或资源范围。

示例：

- Northline 数据源管理。
- Northline 问数配置管理。
- DocuMind 知识库管理。
- DocuMind 文档上传管理。
- DocuMind RAG 配置管理。

权限声明可以采用结构化格式：

```json
{
  "systemCode": "documind",
  "role": "knowledge-admin",
  "permissions": [
    "documind:knowledge-base:manage",
    "documind:document:upload"
  ],
  "scopes": [
    {
      "scopeType": "knowledgeBase",
      "scopeCode": "kb_product"
    }
  ]
}
```

## 权限配置方式

门户需要支持：

- 按用户配置权限。
- 按角色配置权限。
- 按系统配置管理员。
- 按模块配置管理员范围。
- 批量授权和批量取消授权。
- 查看某个用户最终拥有的系统权限。

## 权限生效

权限变更后，应在用户下一次进入子系统时生效。

对于高风险权限变更，例如取消管理员身份，系统可以要求立即失效已有子系统访问凭证。

## 边界

门户负责配置和下发权限声明。子系统负责根据声明执行业务侧展示和校验。

子系统不应绕过门户重新定义全局系统访问权限。

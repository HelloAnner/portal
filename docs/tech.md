# 门户技术方案

## 方案结论

门户系统后端采用 Rust 实现，并与 Northline、DocuMind 的后端实现思路保持一致：以 Rust API 服务作为可信业务边界，前端作为正常 Web 前端消费接口。部署采用单环境部署，应用默认启动即连接 PostgreSQL，数据库不可用时服务应快速失败，避免进入半可用状态。

核心结论：

- 后端：Rust + Axum + Tokio + SQLx + serde + tracing。
- 数据库：PostgreSQL 作为默认且必需的业务数据库。
- 部署：单环境部署，一套运行配置、一套数据库连接、一套门户服务入口。
- 前端：正常使用现有前端工程与交互能力，前端不承载可信身份、权限或会话判断。
- 子系统：Northline、DocuMind 在门户托管模式下信任门户后端签发或换取的身份上下文。

## 项目边界

门户是企业内部系统的统一入口，负责统一登录、用户管理、租户与角色管理、系统目录、权限配置、子系统接入和审计。门户不替代 Northline 的问数业务逻辑，也不替代 DocuMind 的文档 RAG 业务逻辑；门户只负责这些系统进入前的身份、权限和访问上下文。

在门户托管模式下：

- 用户先登录门户。
- 门户后端根据用户、租户、角色、系统目录和权限配置计算可见、可进入的系统。
- 用户进入子系统时，门户后端签发短时凭证或一次性授权码。
- 子系统后端向门户校验或换取身份上下文，再初始化自己的业务会话。

## 总体架构

```text
Browser
  |
  |  HTML/CSS/JS + API calls
  v
Portal Web Frontend
  |
  |  /api/*
  v
Portal Rust Backend
  |
  |  SQLx
  v
PostgreSQL

Portal Rust Backend
  |
  |  ticket / token / identity context
  v
Northline / DocuMind
```

门户后端是唯一可信控制面。前端可以展示登录页、门户首页和管理后台页面，但用户身份、会话有效性、权限计算、子系统跳转凭证和审计写入都必须由 Rust 后端完成。

## 后端方案

后端采用与 Northline、DocuMind 相同的 Rust 服务实现逻辑，推荐技术组合如下：

| 能力 | 技术选择 | 说明 |
| --- | --- | --- |
| Web 框架 | Axum | 路由、中间件、请求提取器和响应封装 |
| 异步运行时 | Tokio | 异步 I/O、任务调度和服务运行 |
| 数据库访问 | SQLx | PostgreSQL 连接池、事务和类型化查询 |
| 配置 | dotenvy + 环境变量 | 本地和部署环境统一读取 `.env` |
| 序列化 | serde / serde_json | API 请求响应、权限上下文、审计快照 |
| 日志追踪 | tracing / tracing-subscriber | 请求链路、审计辅助和问题定位 |
| 认证凭证 | jsonwebtoken / bcrypt / rand | JWT、密码摘要、短时授权码 |
| 错误处理 | thiserror / anyhow | 领域错误和启动错误分层 |

建议服务模块：

| 模块 | 职责 |
| --- | --- |
| `auth` | 登录、退出、会话、当前用户、子系统授权码换取 |
| `users` | 用户资料、账号状态、租户成员关系、角色关系 |
| `tenants` | 租户维护、租户内成员、租户内系统启用 |
| `roles` | 角色、角色成员、角色授权 |
| `systems` | 子系统目录、入口地址、状态、接入元数据 |
| `permissions` | 权限配置、最终权限计算、权限预览 |
| `sub_admins` | 子系统管理员授权、范围和有效期 |
| `integrations` | 子系统接入配置、回调、健康检查和密钥材料 |
| `audits` | 登录、跳转、管理操作和权限变更审计 |

## PostgreSQL 基线

门户默认启动必须连接 PostgreSQL。PostgreSQL 保存门户运行所需的核心数据，包括用户、租户、角色、系统目录、权限、子系统管理员、接入配置、会话、子系统授权码和审计。

默认本地连接约定：

```env
PG_HOST=127.0.0.1
PG_PORT=5432
PG_DATABASE=portal
PG_USER=portal
PG_PASSWORD=portal
PG_SCHEMA=portal
```

启动要求：

- 服务启动时创建 PostgreSQL 连接池并执行健康检查。
- 数据库不可连接、账号无权限或 schema 不可用时，服务启动失败。
- 所有业务查询通过连接池访问 PostgreSQL，不使用前端本地状态作为可信数据来源。
- 迁移脚本由后端工程维护，部署时先迁移数据库，再启动服务。
- 开发环境可以自动创建 schema；部署环境应由迁移流程显式创建和变更。

## 单环境部署

门户采用单环境部署，不设计多套运行环境之间的复杂编排。一个部署单元内只维护一份门户配置，并连接一套 PostgreSQL。

部署形态建议：

```text
/opt/portal/
  bin/portal-api
  shared/.env
  static/
  logs/
```

运行方式：

1. 构建前端产物。
2. 构建 Rust 后端二进制。
3. 将前端静态产物和 Rust 二进制发布到同一部署环境。
4. 在同一份 `.env` 中配置端口、数据库、密钥、Cookie 和子系统接入参数。
5. 执行数据库迁移。
6. 启动门户服务。

前端静态资源可以由 Rust 服务直接托管，也可以由同一环境中的静态文件服务或反向代理托管；但 API 可信边界仍然是 Rust 后端，且前端与后端部署配置必须属于同一环境。

## 前端方案

前端部分正常使用即可，重点是保持页面体验和管理后台功能完整。现有前端可以继续负责：

- 登录页、门户首页、我的资料、我的权限。
- 管理后台页面：用户、租户、角色、系统、权限、子系统管理员、接入配置、审计。
- 表单校验、列表筛选、弹窗、抽屉、空状态和错误提示。

前端不负责：

- 判断用户是否真实登录。
- 自行生成会话或子系统跳转凭证。
- 在浏览器中保存长期敏感令牌。
- 直接拼接用户 ID、角色或权限传给子系统。
- 绕过后端进行权限计算。

前端和后端的集成方式应固定为 API 调用。前端遇到 `AUTH_REQUIRED`、`PERMISSION_DENIED`、`SYSTEM_DISABLED`、`TENANT_DISABLED` 等稳定错误码时，根据错误码展示登录、无权限、申请权限或返回首页动作。

## API 约定

门户后端 API 使用 `/api` 前缀，响应保持统一结构：

```json
{
  "data": {},
  "requestId": "req_...",
  "error": null
}
```

错误结构：

```json
{
  "data": null,
  "requestId": "req_...",
  "error": {
    "code": "PERMISSION_DENIED",
    "message": "当前用户没有访问该系统的权限"
  }
}
```

基础错误码：

- `AUTH_REQUIRED`
- `PERMISSION_DENIED`
- `SYSTEM_DISABLED`
- `TENANT_DISABLED`
- `INVALID_SUBSYSTEM_TICKET`
- `VALIDATION_FAILED`
- `CONFLICT`
- `INTERNAL_ERROR`

管理类写操作必须写入审计。跨子系统可信接口必须使用服务端凭证、签名或短时授权码校验，不能信任浏览器 URL 中的身份明文。

## 子系统接入

Northline 和 DocuMind 保持各自业务后端，但在门户托管模式下，生产访问链路以门户身份为准。

推荐默认使用一次性授权码模式：

1. 用户在门户点击进入子系统。
2. 门户后端校验用户、租户、系统状态和最终权限。
3. 门户后端生成短时、一次性、只保存摘要的授权码。
4. 浏览器跳转到子系统回调地址并携带授权码。
5. 子系统后端携带服务端凭证调用门户 `/api/auth/exchange-ticket`。
6. 门户返回用户、租户、系统角色、权限、管理员范围和有效期。
7. 子系统后端建立自己的业务访问上下文。

JWT 模式可以作为补充方案，用于对子系统只需要校验签名且不需要服务端换取上下文的场景。默认仍建议授权码模式，减少身份上下文在浏览器侧暴露。

## 目录建议

为了和 Northline、DocuMind 的工程组织保持一致，后续可以将门户整理为类似结构：

```text
apps/api-rs/        # Rust 后端服务
apps/web/           # 前端工程
crates/web_embed/   # 可选：将前端静态产物内嵌到 Rust 二进制
docs/               # 产品、设计、技术和功能域文档
```

如果当前阶段暂不调整前端目录，也应保证后端 Rust 工程成为唯一 API 实现，前端通过配置指向 Rust API。

## 迁移要求

现有前端页面可以保留，但 API 实现需要从前端框架内的路由逐步迁移到 Rust 后端。

迁移顺序建议：

1. 建立 Rust 服务骨架、配置读取、PostgreSQL 连接池、健康检查和统一错误响应。
2. 迁移登录、会话、当前用户和退出接口。
3. 迁移门户首页、系统入口和子系统授权码接口。
4. 迁移用户、租户、角色、权限、系统目录和子系统管理员管理接口。
5. 迁移接入配置、安全审计和导出接口。
6. 移除或禁用前端框架内的同名后端 API 路由。

验收标准：

- 无 PostgreSQL 时门户服务无法正常启动。
- 本地默认 PostgreSQL 配置可直接启动门户。
- 前端页面可以正常登录、浏览门户首页、进入授权系统和访问管理后台。
- 所有身份、权限和子系统跳转逻辑都由 Rust 后端完成。
- Northline、DocuMind 能通过门户授权码或令牌获得一致的用户上下文。
- 部署只依赖一套 `.env` 和一套 PostgreSQL 连接，不再拆分多环境配置。

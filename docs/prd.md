# 门户系统 PRD

## 1. 项目定位

门户系统是企业内部各类业务系统的统一入口，也是企业内部用户身份、角色、系统访问权限与子系统管理能力的核心组件。

门户不只是一个导航页，而是企业内部系统治理的上层控制面。Northline、DocuMind 等子系统理论上都具备独立部署能力，也可以拥有各自独立的登录与认证模块。接入门户后，子系统通过配置开关进入门户托管认证模式，关闭或旁路自身登录认证入口，并基于门户传递的用户身份、系统权限与管理员定位来展示对应页面和功能。

## 2. 背景与目标

当前 Northline 和 DocuMind 等子系统存在各自的登录、认证、超级管理员或管理入口能力。后续目标不是否认子系统具备独立登录能力，而是在接入门户的部署模式下，将这些通用身份治理能力统一收敛到门户中，由门户作为企业内部集成场景的认证与授权入口。

目标包括：

- 由门户统一管理企业用户、角色、认证状态与会话入口。
- 由门户超级管理员配置用户可见、可进入、可管理的子系统范围。
- 在门户中定义某个用户是否为某个子系统、某个模块或某个业务域的子管理员。
- 子系统接入门户并开启门户托管认证后，不再承担生产访问链路上的用户登录、认证、全局超级管理员定义等职责。
- 子系统只消费门户传递的身份上下文，并据此决定展示页面、功能入口和模块管理能力。
- Northline 的超级管理员等全局管理能力，在门户托管模式下应关闭或迁移到门户统一定义和下发。
- DocuMind 的登录与认证能力，在门户托管模式下应关闭或旁路，改由门户统一承接。

## 3. 核心原则

### 3.1 门户统一管理身份与权限

门户是企业内部用户身份与访问权限的唯一可信来源。用户是否可以看到某个系统、是否可以进入某个系统、进入后以什么身份使用系统，都由门户统一决定。

### 3.2 子系统保留独立部署能力，通过开关接入门户

每个子系统可以拥有自己的登录模块和认证模块，以支持独立部署、私有化部署或未接入门户的运行模式。

在独立部署模式下，每个子系统可以支持不同的登录方式，例如账号密码、企业 SSO、LDAP、OAuth 或其他自身业务需要的认证方式。门户不限制子系统独立部署时的登录实现。

当子系统接入门户并在 `.env` 中开启门户托管认证后，生产访问链路不再使用子系统本地登录页、本地认证流程、本地会话入口或本地全局超级管理员入口。

子系统可以保留自身业务权限、业务配置和模块级功能逻辑，但用户身份、登录态、基础系统可访问性和管理员定位由门户提供。

### 3.3 子系统通过配置声明是否受门户管理

每个子系统需要在自身 `.env` 配置中声明是否已接入门户，并受门户统一管理。该配置用于控制子系统是否启用门户认证模式。

示例配置方向：

```env
PORTAL_MANAGED=true
PORTAL_AUTH_ENABLED=true
PORTAL_ISSUER=https://portal.example.com
```

具体字段名可在实现阶段根据项目技术栈确定，但语义必须明确：子系统当前是否开启门户托管认证，以及是否关闭或旁路本地登录模块。

### 3.4 门户进入子系统时传递用户上下文

用户从门户点击进入 Northline、DocuMind 或其他子系统时，门户需要携带特定信息给子系统，用于告知子系统当前用户是谁、拥有哪些角色、是否为该系统或模块的管理员。

子系统依据这些信息展示不同页面。例如：

- 普通用户进入后只看到可使用的业务页面。
- Northline 子管理员进入后看到问数系统的管理入口。
- DocuMind 子管理员进入后看到文档库、知识库或 RAG 配置相关管理入口。
- 门户超级管理员进入门户后台时，可以配置所有用户和所有子系统权限。

## 4. 用户与角色定义

门户需要支持以下角色与身份类型。

### 4.1 门户超级管理员

门户超级管理员负责整个门户平台及其接入子系统的管理。

核心能力：

- 管理企业用户。
- 管理门户角色。
- 管理子系统列表。
- 配置不同用户可见、可访问的系统。
- 配置用户是否为某个系统或模块的子管理员。
- 查看关键操作审计记录。
- 管理子系统接入配置。

### 4.2 门户普通用户

门户普通用户登录门户后，只能看到自己有权限访问的系统入口。

核心能力：

- 登录门户。
- 查看自己可访问的系统列表。
- 点击进入授权子系统。
- 在子系统内以门户下发的身份上下文使用业务功能。

### 4.3 子系统管理员

子系统管理员不是子系统内部独立定义的超级管理员，而是由门户配置并下发给子系统的一种用户定位。

一个用户可以是：

- Northline 管理员。
- DocuMind 管理员。
- 某个子系统内特定模块的管理员。
- 多个子系统的管理员。

子系统管理员的实际业务管理能力由子系统根据门户传入的管理员标识、角色列表、权限声明和模块范围决定。

## 6. 门户完整功能描述

### 6.1 统一登录

门户提供统一登录入口。用户访问门户后，由门户完成身份认证。认证成功后，门户建立用户会话，并基于该用户的角色和权限生成可访问系统列表。

接入门户并开启门户托管认证的子系统，在生产访问链路中不展示自己的登录页。若用户直接访问子系统，子系统应根据接入配置判断自身是否处于门户托管模式：若已托管，则引导用户回门户完成登录或通过门户认证机制校验访问上下文；若未托管，则可以继续使用自身独立登录模块。

### 6.2 系统入口聚合

门户根据用户权限展示可见系统入口。不同用户看到的系统列表可能不同。

系统入口至少包含：

- 系统名称。
- 系统描述。
- 系统图标。
- 系统访问地址。
- 系统启用状态。
- 当前用户在该系统中的定位，例如普通用户、系统管理员、模块管理员。

### 6.3 用户管理

门户负责维护企业用户基础信息。

用户信息至少包括：

- 用户 ID。
- 用户名。
- 显示名称。
- 邮箱或手机号。
- 账号状态。
- 所属组织或部门。
- 门户角色。
- 可访问子系统。
- 子系统管理员配置。

### 6.4 角色管理

门户支持定义平台角色。角色用于描述用户在门户层面的身份和管理范围。

基础角色包括：

- 门户超级管理员。
- 门户普通用户。
- 子系统管理员。

后续可以扩展为更细粒度角色，例如组织管理员、系统接入管理员、审计查看员等。

### 6.5 权限配置

门户支持由超级管理员配置用户与子系统之间的权限关系。

权限配置至少包括：

- 用户是否可见某个系统入口。
- 用户是否可进入某个系统。
- 用户进入该系统时的角色。
- 用户是否为该系统管理员。
- 用户是否为该系统某个模块管理员。
- 用户在子系统中的权限声明。

### 6.6 子系统管理员配置

门户需要支持按系统配置子管理员。例如某用户是 Northline 管理员，但不是 DocuMind 管理员；另一个用户可以同时是 Northline 和 DocuMind 管理员。

子管理员配置需要支持不同范围：

- 系统级管理员。
- 模块级管理员。
- 资源级管理员。
- 组织范围管理员。

具体范围由子系统能力决定，门户需要支持以结构化方式保存和下发。

### 6.7 子系统接入配置

每个接入门户的子系统需要在门户侧登记，并在子系统侧声明接入模式。

门户侧配置包括：

- 系统编码。
- 系统名称。
- 系统描述。
- 系统入口 URL。
- 回调 URL 或认证校验 URL。
- 是否启用。
- 是否要求门户托管认证。
- 子系统独立部署时支持的登录方式说明。
- 支持的权限声明类型。

子系统侧配置包括：

- 是否由门户管理。
- 是否保留本地登录模块。
- 是否在当前部署中关闭或旁路本地登录模块。
- 门户认证发行方。
- 门户公钥或校验端点。
- 子系统编码。
- 是否允许本地开发模式绕过门户认证。

### 6.8 进入子系统时的信息传递

门户进入子系统时，应传递可校验、不可被客户端随意伪造的身份上下文。

上下文建议包含：

```json
{
  "userId": "u_001",
  "username": "zhangsan",
  "displayName": "张三",
  "email": "zhangsan@example.com",
  "systemCode": "northline",
  "portalRoles": ["user"],
  "systemRoles": ["admin"],
  "adminScopes": [
    {
      "systemCode": "northline",
      "scopeType": "module",
      "scopeCode": "query-management"
    }
  ],
  "permissions": ["northline:query:manage"],
  "issuedAt": 1781323200,
  "expiresAt": 1781326800
}
```

传递方式可在实现阶段确定，推荐使用短时有效、可签名校验的令牌，或服务端换取身份上下文的方式，避免直接信任前端 URL 参数。

### 6.9 子系统侧行为

接入门户并开启门户托管认证后，子系统需要按以下方式工作：

- 生产访问链路不展示本地登录页。
- 本地认证模块保留在代码或部署能力中，但通过配置关闭、旁路或降级为非生产调试能力。
- 本地全局超级管理员入口在门户托管模式下关闭，管理员身份由门户下发。
- 校验门户传递的身份上下文。
- 根据用户在该子系统中的角色、管理员范围和权限声明展示对应页面。
- 当身份上下文缺失、过期或无效时，引导用户回门户。
- 对关键业务操作仍可保留子系统自己的业务审计。

### 6.10 Northline 调整方向

Northline 作为企业数据库问数系统，可以保留独立部署所需的登录认证模块。但在门户托管模式下，应关闭或旁路内部登录认证入口，并关闭内部超级管理员入口，将管理员身份改由门户统一定义和下发。

门户负责：

- 判断用户是否可见 Northline。
- 判断用户是否可进入 Northline。
- 判断用户是否是 Northline 管理员。
- 判断用户是否拥有 Northline 特定模块管理能力。

Northline 负责：

- 消费门户下发的用户身份。
- 消费门户下发的 Northline 角色和权限声明。
- 展示问数、数据源、权限、配置等业务页面。
- 根据门户下发的管理员定位展示管理入口。

### 6.11 DocuMind 调整方向

DocuMind 作为企业文档 RAG 系统，可以保留独立部署所需的登录认证模块。但在门户托管模式下，应关闭或旁路内部登录认证入口，将用户身份与管理员定位改由门户统一承接。

门户负责：

- 判断用户是否可见 DocuMind。
- 判断用户是否可进入 DocuMind。
- 判断用户是否是 DocuMind 管理员。
- 判断用户是否拥有知识库、文档库、RAG 配置等模块的管理能力。

DocuMind 负责：

- 消费门户下发的用户身份。
- 消费门户下发的 DocuMind 角色和权限声明。
- 展示文档检索、知识库、RAG 问答、配置管理等业务页面。
- 根据门户下发的管理员定位展示管理入口。

## 7. 登录关系说明

门户与子系统之间的登录关系如下：

1. 用户访问门户。
2. 门户完成登录与认证。
3. 门户根据用户身份加载可见系统与权限。
4. 用户点击某个子系统。
5. 门户生成或交换一次可校验的子系统访问凭证。
6. 子系统校验门户凭证。
7. 子系统建立自身的短期访问上下文，或每次请求都校验门户凭证。
8. 子系统根据用户身份、系统角色、管理员范围和权限声明展示页面。
9. 当凭证过期或无效时，子系统引导用户回门户重新认证。

这意味着在门户托管认证模式下，用户只需要登录门户一次。子系统仍可保留独立登录模块用于非门户部署，但在接入门户的生产链路中不再独立要求用户登录。

## 8. 非目标

当前 PRD 不要求门户直接实现所有子系统内部业务权限细节。

非目标包括：

- 不在门户中重写 Northline 的问数业务逻辑。
- 不在门户中重写 DocuMind 的 RAG 和文档处理逻辑。
- 不要求门户管理所有子系统内部资源的每个细粒度操作。
- 不要求子系统完全删除业务权限判断，子系统仍可根据门户声明执行业务级判断。
- 不要求子系统从代码层面完全移除独立登录模块；子系统仍可支持独立部署，只是在门户托管模式下关闭或旁路本地登录认证。

## 9. 验收标准

- `docs/prd.md` 能清楚说明门户定位、统一认证边界、子系统接入模式和完整功能概览。
- 文档明确说明 Northline 和 DocuMind 的登录、认证、超级管理员等通用能力在门户托管模式下应收敛到门户。
- 文档明确说明子系统可以保留独立登录认证模块，但在门户托管模式下通过配置关闭或旁路本地登录认证。
- 文档明确说明子系统通过 `.env` 声明是否由门户管理。
- 文档明确说明门户进入子系统时需要传递用户基本信息、角色、权限和管理员定位。
- `docs` 下按功能域拆分多个目录，每个目录包含详细功能说明。

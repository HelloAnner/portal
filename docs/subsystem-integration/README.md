# 子系统接入

## 功能定位

子系统接入功能定义 Northline、DocuMind 等系统如何接入门户，以及接入后如何与门户完成身份、权限和管理员定位的协作。

## 相关方案

- [门户登录态对接 Northline 与 DocuMind 方案](./PORTAL_SSO_NORTHLINE_DOCUMIND.md)：梳理当前门户、Northline、DocuMind 的认证现状，并定义门户登录后携带身份上下文进入子系统的对接协议、角色映射和实施步骤。

## 接入原则

子系统可以有两种部署模式：

- 独立部署模式：使用子系统自己的登录模块、认证模块和会话机制。
- 门户托管模式：通过配置关闭或旁路子系统本地登录认证，由门户统一完成登录、认证和基础授权。

接入门户并开启门户托管模式的子系统必须遵循：

- 生产访问链路不再提供独立登录入口。
- 本地认证系统可以保留，但不作为当前部署的认证入口。
- 本地全局超级管理员入口关闭，管理员身份由门户配置并下发。
- 使用门户用户 ID 作为用户身份来源。
- 校验门户传递的身份上下文。
- 根据门户下发的权限声明展示页面和功能。

## 门户侧配置

门户需要为每个子系统维护：

- 系统编码。
- 系统名称。
- 系统描述。
- 系统图标。
- 入口地址。
- 是否启用。
- 是否门户托管认证。
- 支持的角色列表。
- 支持的权限声明列表。
- 管理员范围定义。
- 凭证校验方式。

## 子系统侧 `.env` 配置

子系统需要通过 `.env` 声明是否接入门户。

示例：

```env
SYSTEM_CODE=northline
PORTAL_MANAGED=true
PORTAL_AUTH_ENABLED=true
PORTAL_ISSUER=https://portal.example.com
PORTAL_PUBLIC_KEY_PATH=/app/config/portal-public-key.pem
PORTAL_AUTH_CALLBACK=/auth/portal/callback
```

语义说明：

- `SYSTEM_CODE`：子系统编码，需要与门户登记编码一致。
- `PORTAL_MANAGED`：是否由门户管理。
- `PORTAL_AUTH_ENABLED`：是否启用门户认证。
- `PORTAL_AUTH_ENABLED=true` 时，子系统应关闭或旁路本地登录认证入口。
- `PORTAL_ISSUER`：门户认证凭证发行方。
- `PORTAL_PUBLIC_KEY_PATH`：用于校验门户签名凭证的公钥。
- `PORTAL_AUTH_CALLBACK`：子系统接收或处理门户认证回调的地址。

字段名不是最终约束，实际实现可根据项目现状调整，但必须保留这些配置语义。

独立部署模式下，子系统可以继续保留自身支持的登录方式，门户不要求这些登录方式保持一致。门户只要求在 `PORTAL_MANAGED=true` 且 `PORTAL_AUTH_ENABLED=true` 的部署中，生产访问链路以门户认证为准。

## 身份上下文

门户传递给子系统的身份上下文至少包含：

- 用户 ID。
- 用户名。
- 显示名称。
- 邮箱。
- 目标系统编码。
- 门户角色。
- 用户在目标系统中的角色。
- 用户在目标系统中的权限声明。
- 管理员范围。
- 签发时间。
- 过期时间。

## Northline 接入要求

Northline 接入门户后：

- 保留独立部署所需的内部登录认证模块。
- 在门户托管模式下关闭或旁路内部登录认证入口。
- 在门户托管模式下关闭内部超级管理员入口，管理员身份由门户下发。
- 使用门户传入的用户 ID 识别用户。
- 根据 `northline` 相关角色和权限声明展示问数、数据源和管理入口。

## DocuMind 接入要求

DocuMind 接入门户后：

- 保留独立部署所需的内部登录认证模块。
- 在门户托管模式下关闭或旁路内部登录认证入口。
- 使用门户传入的用户 ID 识别用户。
- 根据 `documind` 相关角色和权限声明展示文档检索、知识库、RAG 配置和管理入口。

## 未接入门户的子系统

如果某个子系统尚未接入门户，或当前部署选择独立部署模式，可以继续使用自身登录方式。但一旦 `.env` 声明进入门户托管模式，生产访问就应以门户认证为准。
